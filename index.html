Ticket Management System — API Payload Reference

Complete request/response payload documentation for every endpoint, grouped by presenter section. Every controller in this project is a @RestController — the API is pure JSON in / JSON out (except the QR PNG, ticket PDF, CSV exports, and the multipart upload endpoints).

Base URL: http://localhost:8010 Spring Boot 3.5.9 · Java 17 Swagger UI: /swagger-ui.html Auth: HTTP Basic + session cookie CSRF: disabled

Standard error envelope

All errors flow through ApiExceptionHandler. Any endpoint below can return this shape: 

// 400 Bad Request  (IllegalArgumentException)
{
  "error": "Please enter a ticket number.",
  "type":  "BAD_REQUEST"
}
// 409 Conflict  (IllegalStateException)
{
  "error": "Your seat hold expired. Please reselect seats.",
  "type":  "CONFLICT"
}
Other codes: 401 unauthenticated on protected routes · 403 non-admin on /admin/** · 413 FILE_TOO_LARGE on oversized uploads · 500 STORAGE_FAILED on disk write failure.

Presenters

Slide Title: How Every Request Flows
• A client sends an HTTP request to the application.
• The request is handled by a controller using annotations such as @RestController, @RequestMapping, @GetMapping, and @PostMapping.
• The controller passes the request to the service layer for business logic processing.
• The service layer communicates with the repository, which uses Spring Data JPA to access the database.
• Data is stored and retrieved from PostgreSQL, and the result is returned back to the client.

Controllers at a Glance
• Public controllers handle movie browsing, showtimes, and booking pages.
• Auth and ticket controllers manage login, registration, and ticket-related actions.
• Booking and seat-hold controllers support seat selection and reservation.
• Admin controllers manage movies, halls, showtimes, bookings, users, food, promos, reports, and settings.
• All endpoints are documented through Swagger UI for easy testing and review.

3. Hai Bunleap — Authentication & Tickets

HBHai Bunleap How a user gets identity into the system, and how an issued ticket is looked up, displayed, scanned and printed.
3.1POST/loginPublic

What it is used for: Authenticates email + password through Spring Security's AuthenticationManager, saves the SecurityContext into the HTTP session (so a JSESSIONID cookie is set), and hands back a JWT. It also tells the client where to go next based on role.

Request payload · application/json — LoginRequest 

{
  "email":    "admin@tkm.co",   // @NotBlank
  "password": "Admin@123"       // @NotBlank
}

Response 200 · LoginResponse

{
  "email":       "admin@tkm.co",
  "role":        "ADMIN",             // "ADMIN" if ROLE_ADMIN is granted, else "CUSTOMER"
  "redirectUrl": "/admin/dashboard",  // "/movies" for customers
  "token":       "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhZG1pbkB0a20uY28i…"
}
Two ways to stay authenticated afterwards: reuse the session cookie, or send Authorization: Basic <base64(email:password)> on each request. SUSPENDED / BANNED accounts are rejected by CustomUserDetailsService.
3.2POST/registerPublic

What it is used for: Self-service sign-up. Always creates a CUSTOMER; the role can never be escalated from this endpoint. The password is BCrypt-hashed before storage.

Request payload · application/json — RegisterForm (bean-validated) 

{
  "name":     "Sok Dara",          // @NotBlank
  "email":    "dara@example.com",  // @NotBlank @Email — must be unique
  "password": "secret123"          // @NotBlank
}

Response 200

{ "success": true }
400 if validation fails or the email is already registered.

4. Chhun Sopheaktra — Booking System

CSChhun Sopheaktra The checkout funnel end to end, plus the real-time seat-hold layer that stops two people buying the same seat.
The happy path: GET seats → POST /api/seat-holds/hold → GET checkout (preview totals) → POST checkout (confirm) → GET confirmation. Holds are keyed by HTTP session id, so the same cookie must be sent throughout.

Request payload

No body. The HTTP session is read implicitly to work out which holds are yours.

9.6GETController Example — /admin/movies (CRUD walkthrough)

What it is used for: The closing demo. AdminMovieController is the clearest illustration of the project's conventions: a thin @RestController that only delegates, a create-or-update POST keyed on the presence of id, springdoc annotations for Swagger, and errors thrown as exceptions rather than hand-built payloads.

The four operations at a glance

# Method Request payload Response

The controller

@RestController
@RequestMapping("/admin/movies")
@RequiredArgsConstructor
@Tag(name = "Admin: Movies", description = "Back-office movie management")
public class AdminMovieController {

    private final MovieService movieService;   // constructor-injected by Lombok

    @GetMapping(produces = APPLICATION_JSON_VALUE)
    public ResponseEntity<List<Movie>> movies() {
        return ResponseEntity.ok(movieService.findAll());
    }

    @GetMapping(value = "/{id}", produces = APPLICATION_JSON_VALUE)
    public ResponseEntity<Movie> movie(@PathVariable Long id) {
        return ResponseEntity.ok(movieService.findById(id));
    }

    @PostMapping(consumes = MULTIPART_FORM_DATA_VALUE, produces = APPLICATION_JSON_VALUE)
    public ResponseEntity<Movie> saveMovie(
            @ModelAttribute Movie movie,                                // form fields → entity
            @RequestPart(value = "imageFile",  required = false) MultipartFile imageFile,
            @RequestPart(value = "bannerFile", required = false) MultipartFile bannerFile) {
        return ResponseEntity.ok(movieService.saveWithImages(movie, imageFile, bannerFile));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteMovie(@PathVariable Long id) {
        movieService.delete(id);
        return ResponseEntity.noContent().build();
    }
}

Conventions this project follows

Rule Why
Controllers stay thin — all logic lives in service/ Keeps HTTP concerns separate from business rules and makes the service unit-testable
Endpoint-local DTOs are records nested in the controller Request/response shapes live next to the endpoint that owns them, instead of a sprawling dto/ package
Never serialize an entity with uninitialized lazy relations spring.jpa.open-in-view=false, so Jackson would hit LazyInitializationException. Flat entities (Movie, Cinema, FoodItem, PromoCode, Notification, SystemSetting) are safe to return directly; anything that walks a relation is mapped to a record inside a @Transactional(readOnly = true) method
Throw IllegalArgumentException / IllegalStateException ApiExceptionHandler turns them into 400 / 409 with a consistent envelope — no error payloads assembled by hand
Annotate with @Tag / @Operation Endpoints appear grouped and described in Swagger UI at /swagger-ui.html
One POST for create and update, keyed on id Halves the endpoint count and lets a single admin form serve both cases
